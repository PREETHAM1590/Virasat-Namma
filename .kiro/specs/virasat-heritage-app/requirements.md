# Requirements Document

## Introduction

Virasat (ವಿರಾಸತ್ — meaning "Heritage" in Kannada) is a cultural tourism companion Android application for exploring Karnataka's rich heritage sites. The app serves travellers, students, history enthusiasts, and cultural tourists by providing immersive discovery, AI-powered narration, gamified check-ins, offline access, and a multilingual experience in English and Kannada.

The application is built with Kotlin and Jetpack Compose targeting Android API 26–35. It integrates Firebase (Firestore, Authentication, Analytics), Room (local persistence), Google Maps, ML Kit (QR scanning), Gemini AI (REST), CameraX, and biometric authentication to deliver a full-featured heritage exploration platform.

This document specifies all functional and non-functional requirements for the complete Virasat application.

## Glossary

- **App**: The Virasat Android application.
- **User**: An authenticated person using the App.
- **Guest**: A person who has not yet completed authentication.
- **HeritageSite**: A Karnataka cultural or natural landmark with structured metadata (name, location, type, history, coordinates, gallery, facts, visiting hours, entry fee, QR code, audio guide).
- **SiteType**: An enumeration of heritage site categories: TEMPLE, PALACE, FORT, MONUMENT, CAVE, UNESCO, JAIN, MUSEUM, NATURE, TREK, LAKE, MISC.
- **CheckIn**: A record created when a User scans a valid QR code at a HeritageSite, capturing site identity, timestamp, and stamp icon.
- **Fact**: A discrete piece of knowledge associated with a HeritageSite, which may be locked or unlocked.
- **UnlockedFact**: A Fact that has been revealed to the User via QR scan at the corresponding HeritageSite.
- **Passport**: The Travel Passport screen displaying all CheckIn stamps earned by the User.
- **Badge**: A digital achievement awarded to the User upon reaching defined check-in or exploration milestones.
- **Leaderboard**: A ranked list of Users ordered by total check-in count.
- **AI_Assistant**: The Gemini-powered conversational heritage guide accessible from the Home screen.
- **AI_Tour**: The AI Narrated Tour feature that generates spoken narration scripts for a specific HeritageSite.
- **Talking_Tour**: The Street View + AI feature that analyses live panoramic views and provides contextual narration.
- **Audio_Guide**: A chapter-based audio playback experience for a HeritageSite.
- **Repository**: The data access layer (HeritageRepository interface) backed by either Firestore or Room.
- **Firestore**: Google Cloud Firestore used as the remote data source.
- **Room_DB**: The local SQLite database managed by Room, used for offline access.
- **Gemini_Service**: The GeminiHeritageService that communicates with the Gemini 2.0 Flash REST API.
- **Auth_Service**: The FirebaseAuthService managing email/password and Google Sign-In authentication.
- **Locale**: The active language setting of the App (English: "en", Kannada: "kn").
- **Biometric_Auth**: Fingerprint or strong biometric authentication via Android BiometricPrompt.
- **Secure_Prefs**: EncryptedSharedPreferences used to store sensitive user data.
- **Weather_Widget**: A UI component on the Home screen displaying current temperature and weather condition based on the User's GPS location.
- **Itinerary**: A user-curated ordered list of HeritageSites to visit.
- **Quiz**: An interactive trivia game generated by Gemini_Service based on HeritageSite facts.
- **Community**: A social screen where Users share experiences and posts about heritage sites.
- **Analytics**: Firebase Analytics event tracking for screen views and user interactions.

## Requirements

### Requirement 1: App Launch and Navigation Initialisation

**User Story:** As a first-time visitor, I want the app to guide me through language selection and onboarding before reaching the login screen, so that I start with the correct language and understand the app's value.

#### Acceptance Criteria

1. WHEN the App is launched for the first time, THE App SHALL display the SplashScreen for a minimum of 1 second before navigating to the LanguageScreen.
2. WHEN the onboarding flow has not been completed, THE App SHALL navigate from SplashScreen to LanguageScreen to OnboardingScreen to LoginScreen in that order.
3. WHEN the onboarding flow has been completed and the User is not authenticated, THE App SHALL navigate directly from SplashScreen to LoginScreen.
4. WHEN the onboarding flow has been completed and the User is authenticated, THE App SHALL navigate directly from SplashScreen to HomeScreen.
5. THE App SHALL persist the onboarding completion flag in SharedPreferences under the key "onboarding_seen" so that the flag survives app restarts.
6. FOR ALL language codes set via LocaleHelper.setLocale, LocaleHelper.getSavedLocale SHALL return the same language code after an app restart (round-trip property).


### Requirement 2: Language Selection

**User Story:** As a User, I want to select my preferred language (English or Kannada) at any time, so that all UI text and site names are displayed in my chosen language.

#### Acceptance Criteria

1. THE App SHALL support English ("en") and Kannada ("kn") as selectable display languages.
2. WHEN the User selects a language on the LanguageScreen, THE App SHALL persist the selection via LocaleHelper.setLocale and apply it immediately to all subsequent screens.
3. WHEN the User navigates to LanguageScreen from SettingsScreen, THE App SHALL return to SettingsScreen after the selection is confirmed.
4. WHEN the active Locale is "kn" and a HeritageSite has a non-empty nameLocal field, THE App SHALL display nameLocal instead of name throughout the UI.
5. WHEN the active Locale is "en", THE App SHALL display the English name field for all HeritageSites.
6. FOR ALL HeritageSite records where nameLocal is non-empty, LocaleHelper.siteName SHALL return nameLocal when locale is "kn" and name when locale is "en" (pure function property).

### Requirement 3: User Authentication — Email and Password

**User Story:** As a Guest, I want to register and log in with my email and password, so that my progress and data are securely tied to my account.

#### Acceptance Criteria

1. WHEN a Guest submits a valid email and password of at least 6 characters on the SignUpScreen, THE Auth_Service SHALL create a Firebase account, set the display name, and create a Firestore user profile document.
2. WHEN a Guest submits a valid email and password on the LoginScreen, THE Auth_Service SHALL authenticate the User and navigate to HomeScreen.
3. WHEN authentication fails, THE Auth_Service SHALL return a human-readable error message via FirebaseAuthService.friendlyError without exposing raw Firebase error codes to the UI.
4. IF the submitted email is already registered, THEN THE Auth_Service SHALL return the message "This email is already registered. Try logging in."
5. IF the submitted password is fewer than 6 characters, THEN THE Auth_Service SHALL return the message "Password must be at least 6 characters."
6. IF the network is unavailable during authentication, THEN THE Auth_Service SHALL return the message "Network error. Check your connection."
7. WHEN the User taps "Forgot Password" on the LoginScreen, THE App SHALL navigate to ForgotPasswordScreen.
8. WHEN a valid email is submitted on the ForgotPasswordScreen, THE Auth_Service SHALL send a Firebase password reset email to that address.
9. FOR ALL Firebase exception messages, FirebaseAuthService.friendlyError SHALL return a non-empty, user-readable string (no raw exception text exposed).

---

### Requirement 4: User Authentication — Google Sign-In

**User Story:** As a Guest, I want to sign in with my Google account, so that I can authenticate quickly without creating a separate password.

#### Acceptance Criteria

1. WHEN the User taps "Sign in with Google" on the LoginScreen, THE Auth_Service SHALL launch the Google Sign-In intent.
2. WHEN the Google Sign-In flow completes successfully, THE Auth_Service SHALL exchange the Google ID token for a Firebase credential and authenticate the User.
3. WHEN a new User signs in with Google for the first time, THE Auth_Service SHALL create a Firestore user profile document with uid, name, email, createdAt, checkInCount, and badgesEarned fields.
4. IF the Google Sign-In flow is cancelled or fails, THEN THE Auth_Service SHALL return a descriptive error message without crashing the App.
5. WHEN Google Sign-In succeeds, THE App SHALL navigate to HomeScreen and clear the back stack.

### Requirement 5: Biometric Authentication

**User Story:** As a User, I want to enable fingerprint login, so that I can access the app quickly without re-entering my password.

#### Acceptance Criteria

1. WHEN the User enables biometric login in SettingsScreen, THE App SHALL store the preference via BiometricHelper.setBiometricEnabled with value true in SharedPreferences.
2. WHEN biometric login is enabled and the User launches the App while authenticated, THE App SHALL offer a BiometricPrompt before granting access to HomeScreen.
3. WHEN biometric authentication succeeds, THE App SHALL grant access to HomeScreen.
4. WHEN biometric authentication fails or is cancelled, THE App SHALL offer the option to use password login instead.
5. IF the device has no biometric hardware, THEN THE App SHALL hide the biometric login option in SettingsScreen.
6. IF the device has biometric hardware but no enrolled biometrics, THEN THE App SHALL display a message directing the User to enrol biometrics in device settings.
7. FOR ALL calls to BiometricHelper.setBiometricEnabled(context, enabled) followed by BiometricHelper.isBiometricEnabled(context), THE App SHALL return the same value as enabled (round-trip property).

### Requirement 6: Critical Bug Fixes

**User Story:** As a User, I want the app's core services to work reliably, so that AI features respond correctly, authentication state is always current, and local data persists without crashes.

#### Acceptance Criteria

1. THE Gemini_Service SHALL NOT configure a certificate pinner on its OkHttpClient; the placeholder SHA-256 pin `AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=` SHALL be removed so that all HTTPS calls to `generativelanguage.googleapis.com` succeed with the standard system trust store.
2. WHEN the Gemini_Service constructs a JSON request payload for any API call, THE Gemini_Service SHALL build the payload using a structured JSON serialiser (e.g., `org.json.JSONObject` or `kotlinx.serialization`) rather than string interpolation, so that special characters in user-supplied text cannot alter the JSON structure.
3. WHEN the App is running and the Firebase authentication state changes (sign-in or sign-out), THE App SHALL reflect the new authentication state in the navigation destination within one recomposition cycle by collecting `FirebaseAuthService.authStateFlow()` as a Compose state rather than reading `FirebaseAuthService.isLoggedIn` once at composition time.
4. THE `Fact` data class SHALL be annotated with `@Serializable` so that `Converters.toFactList` and `Converters.fromFactList` can serialise and deserialise `List<Fact>` via `kotlinx.serialization` without a runtime crash.
5. IF a user-supplied string passed to `Gemini_Service.chatWithHeritageGuide` contains JSON-special characters (double quotes, backslashes, newlines), THEN THE Gemini_Service SHALL escape or encode those characters before embedding them in the request payload, so that the resulting JSON remains structurally valid.
6. FOR ALL valid `List<Fact>` values, `Converters.toFactList` followed by `Converters.fromFactList` SHALL return a list equal to the original (round-trip property).

### Requirement 7: Offline Mode and Bookmarks

**User Story:** As a User, I want to bookmark heritage sites and browse them offline, so that I can plan visits and access site information without an internet connection.

#### Acceptance Criteria

1. THE `RoomHeritageRepository` SHALL implement `toggleBookmark(siteId)` by persisting a bookmark record in Room_DB and returning `true` when the site becomes bookmarked and `false` when it becomes unbookmarked.
2. THE `RoomHeritageRepository` SHALL implement `isBookmarked(siteId)` by querying Room_DB and returning the current bookmark state for the given site identifier.
3. THE `RoomHeritageRepository` SHALL implement `observeBookmarks()` by returning a `Flow<List<String>>` that emits the current list of bookmarked site identifiers and re-emits whenever the bookmark set changes.
4. WHEN the device transitions from offline to online, THE App SHALL sync the User's Firestore bookmark list into Room_DB so that bookmarks created on other devices are available locally.
5. WHEN the device is offline, THE `OfflineScreen` SHALL display all HeritageSites whose identifiers appear in the local bookmark list, allowing the User to browse site details without a network connection.
6. THE `OfflineScreen` SHALL detect the current network state and display a "You are offline" indicator WHILE the device has no active internet connection.
7. WHEN a HeritageSite detail page is viewed while online, THE App SHALL instruct Coil's disk cache to store the site's primary image so that the image is available for offline display.
8. WHEN the User taps a bookmarked site on the `OfflineScreen`, THE App SHALL navigate to the SiteDetailScreen and display cached data from Room_DB.
9. FOR ALL site identifiers `id` where `toggleBookmark(id)` is called an even number of times starting from an unbookmarked state, `isBookmarked(id)` SHALL return `false` (idempotence / toggle invariant property).

### Requirement 8: Smart Badges and Gamification Engine

**User Story:** As a User, I want to earn badges based on my real exploration activity, so that I am motivated to visit more sites and discover more heritage content.

#### Acceptance Criteria

1. THE `BadgesScreen` SHALL derive its badge list from a `BadgeEngine` that evaluates unlock conditions against live User data (check-ins, unlocked facts, site types visited) rather than a hardcoded list.
2. THE `BadgeEngine` SHALL unlock the "Temple Seeker" badge WHEN the User has recorded check-ins at 3 or more HeritageSites of `SiteType.TEMPLE`.
3. THE `BadgeEngine` SHALL unlock the "Fact Collector" badge WHEN the User has unlocked 5 or more distinct Facts across any HeritageSites.
4. THE `BadgeEngine` SHALL unlock the "UNESCO Explorer" badge WHEN the User has recorded a check-in at any HeritageSite of `SiteType.UNESCO`.
5. THE `BadgeEngine` SHALL unlock the "Pathfinder" badge WHEN the User has recorded check-ins at 5 or more unique HeritageSites.
6. THE `BadgeEngine` SHALL unlock the "Quiz Master" badge WHEN the User has completed at least one Quiz session with a score of 100%.
7. THE `BadgeEngine` SHALL unlock the "AI Voyager" badge WHEN the User has used the AI_Tour feature for at least one HeritageSite.
8. WHILE a badge is locked, THE `BadgesScreen` SHALL display a progress indicator showing the User's current count toward the unlock threshold (e.g., "2 / 3 temples visited").
9. WHEN a badge is newly unlocked, THE App SHALL display a congratulatory message to the User on the `BadgesScreen` or via an in-app notification.
10. FOR ALL badge definitions, the `BadgeEngine` SHALL produce a deterministic result: given the same set of check-ins, unlocked facts, and quiz results, the set of unlocked badges SHALL always be identical (pure function property).

### Requirement 9: Push Notifications

**User Story:** As a User, I want to receive timely push notifications about nearby heritage sites, weekly facts, and badge unlocks, so that I stay engaged with Karnataka's heritage even when the app is in the background.

#### Acceptance Criteria

1. THE App SHALL integrate Firebase Cloud Messaging (FCM) and register a device token with Firestore under the authenticated User's profile document on first launch after sign-in.
2. WHEN the User's device location is within 500 metres of a HeritageSite's coordinates, THE App SHALL deliver a local push notification identifying the nearby site and offering a deep link to its detail screen.
3. THE App SHALL send a weekly push notification containing a heritage fact selected from the Firestore `heritageSites` collection, delivered via an FCM scheduled topic message.
4. WHEN the `BadgeEngine` transitions a badge from locked to unlocked, THE App SHALL deliver a local push notification congratulating the User and naming the newly earned badge.
5. THE App SHALL request the `POST_NOTIFICATIONS` runtime permission (Android 13+) before displaying any push notification, and SHALL NOT deliver notifications if the permission is denied.
6. WHEN the User taps a proximity notification, THE App SHALL open the App and navigate directly to the SiteDetailScreen for the identified HeritageSite.
7. WHEN the User taps a badge-unlock notification, THE App SHALL open the App and navigate directly to the `BadgesScreen`.
8. THE App SHALL allow the User to disable each notification category (proximity, weekly facts, badge unlocks) independently via the SettingsScreen.
9. IF the device is offline when a geofence trigger fires, THEN THE App SHALL queue the proximity notification and deliver it once connectivity is restored.

### Requirement 10: Social Sharing and Community

**User Story:** As a User, I want to share my check-ins, post reviews with photos, and see how I rank against other explorers, so that I can celebrate my heritage journey and connect with the community.

#### Acceptance Criteria

1. THE `CommunityScreen` SHALL load and display posts from a Firestore `communityPosts` collection, ordered by timestamp descending, with real-time updates via a Firestore snapshot listener.
2. WHEN the User completes a check-in, THE App SHALL offer the option to share the check-in as an image card composed of the site's primary photo, the site's stamp icon, and the User's display name.
3. WHEN the User chooses to share a check-in card, THE App SHALL render the card as a bitmap and invoke the Android system share sheet so the User can share it to any installed app.
4. THE `ReviewsScreen` SHALL allow the User to submit a review consisting of a text body (1–500 characters) and an optional photo, persisted to a Firestore `reviews` sub-collection under the corresponding HeritageSite document.
5. WHEN a review is submitted, THE App SHALL upload any attached photo to Firebase Storage and store the download URL in the Firestore review document.
6. THE `LeaderboardScreen` SHALL display Users ordered by `checkInCount` descending, sourced from the Firestore `users` collection, and SHALL update in real time via a Firestore snapshot listener.
7. WHEN the User's own entry appears in the leaderboard, THE App SHALL visually highlight the User's row to distinguish it from other entries.
8. IF the `communityPosts` collection is empty or unavailable, THEN THE `CommunityScreen` SHALL display an empty-state message inviting the User to be the first to share.
9. THE App SHALL enforce a maximum review text length of 500 characters and SHALL display a character counter on the review input field.
10. FOR ALL submitted community posts, the Firestore document SHALL include the fields: `userId`, `userName`, `siteId`, `siteName`, `imageUrl` (nullable), `text`, and `timestamp` (server timestamp).

### Requirement 11: Itinerary Planner

**User Story:** As a User, I want to build, save, and share named itineraries of heritage sites ordered by geography, so that I can plan efficient multi-site visits and share my plans with others.

#### Acceptance Criteria

1. THE `ItineraryScreen` SHALL allow the User to search for and add HeritageSites to a new or existing Itinerary from the full site catalogue.
2. WHEN the User adds two or more HeritageSites to an Itinerary, THE `Itinerary_Planner` SHALL automatically order the sites using a nearest-neighbour algorithm starting from the first site added, minimising total straight-line travel distance.
3. THE `Itinerary_Planner` SHALL calculate the straight-line distance between consecutive sites in the ordered Itinerary using the Haversine formula applied to each site's `latitude` and `longitude` fields, and SHALL display the estimated distance in kilometres between each pair of adjacent sites.
4. THE App SHALL allow the User to assign a name (1–100 characters) to each Itinerary and SHALL persist the named Itinerary to Firestore under the authenticated User's profile in a `itineraries` sub-collection.
5. THE App SHALL allow the User to save multiple distinct named Itineraries and SHALL display all saved Itineraries on the `ItineraryScreen`.
6. WHEN the User taps a site within an Itinerary, THE App SHALL navigate to the SiteDetailScreen for that site.
7. THE App SHALL allow the User to export an Itinerary as a shareable deep link of the form `virasat://itinerary/{itineraryId}` that, when opened on a device with the App installed, navigates directly to that Itinerary.
8. WHEN the deep link `virasat://itinerary/{itineraryId}` is opened, THE App SHALL retrieve the Itinerary from Firestore by `itineraryId` and display it on the `ItineraryScreen`.
9. IF an Itinerary contains fewer than 2 sites, THEN THE `Itinerary_Planner` SHALL skip the nearest-neighbour ordering step and display the single site without a distance estimate.
10. FOR ALL Itineraries with 2 or more sites, the nearest-neighbour ordering produced by `Itinerary_Planner` SHALL result in a total route distance less than or equal to the total distance of the original unordered site sequence (optimisation invariant property).
11. FOR ALL pairs of HeritageSite coordinates, `Itinerary_Planner.haversineDistance(lat1, lon1, lat2, lon2)` SHALL equal `Itinerary_Planner.haversineDistance(lat2, lon2, lat1, lon1)` (symmetry property).
